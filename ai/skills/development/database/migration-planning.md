# Skill: Migration Planning

## Purpose

Plan and execute Prisma database migrations safely — ensuring that schema changes are applied without data loss, naming conventions are followed, and each migration is documented and reversible where possible.

## When To Use

Use before running `prisma migrate dev` for any schema change. For changes that affect existing data (adding NOT NULL columns, renaming columns, changing types), a migration plan must be written before the migration is created.

## Required Inputs

- Description of the schema change
- Whether the change affects existing data (is the table currently populated?)
- Target environment (development vs. staging vs. production)
- Rollback requirement (can this be undone?)

## Process

1. Describe the change in plain language.
2. Classify the migration type: additive (safe), modifying (review required), destructive (approval required).
3. For additive: run `prisma migrate dev --name [descriptive-name]` directly.
4. For modifying/destructive: write the migration SQL manually, review it, then apply.
5. Document the migration in CHANGELOG.md.
6. Write a rollback plan (what SQL would undo this change).

## Output Format

```markdown
# Migration Plan — [Name]

**Type:** ADDITIVE / MODIFYING / DESTRUCTIVE
**Affected Tables:** [List]
**Data Impact:** [None / Backfill required / Data loss possible]

## Change Description

[What is being changed and why]

## Migration Command / SQL

```sql
-- Generated by Prisma or written manually
ALTER TABLE "Project" ADD COLUMN "progressPercent" INTEGER NOT NULL DEFAULT 0;
```

## Rollback SQL

```sql
ALTER TABLE "Project" DROP COLUMN "progressPercent";
```

## Pre-Migration Checklist

- [ ] Schema change matches DATA_MODEL.md
- [ ] Migration has a descriptive name (not a timestamp)
- [ ] Data impact assessed
- [ ] Rollback plan written
- [ ] Changelog updated
```

## Validation Rules

- Migration name must be descriptive: `add_project_tasks_table`, `add_health_field_to_project`, not `migration_001`
- DESTRUCTIVE migrations require engineering lead approval before running in staging
- Every migration must have an entry in CHANGELOG.md

## Risk Checks

- Flag if a NOT NULL column is added to a table with existing rows without a default value (will fail)
- Flag if a column is renamed (Prisma generates DROP + ADD which loses data)
- Flag if an index is being dropped on a high-traffic table

## Do Not Do

- Do not run `prisma migrate dev` without a descriptive `--name` flag
- Do not run destructive migrations on staging without a tested rollback plan
- Do not reset the migration history in a shared environment

## Example Output

> Migration: `add_project_milestone_table`. Type: ADDITIVE. Affected tables: new `ProjectMilestone` table. Data impact: none (new table). Command: `prisma migrate dev --name add_project_milestone_table`. Rollback SQL: `DROP TABLE "ProjectMilestone"`. No data impact on existing tables.
