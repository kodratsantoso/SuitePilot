# Skill: BRD Generation

## Purpose

Generate a structured Business Requirements Document (BRD) draft based on discovery session summaries and module recommendations. The BRD captures the customer's business requirements, success criteria, and scope boundaries in a format suitable for functional design and solution architecture work.

## When To Use

Use after discovery sessions are complete and summarized, and the module recommendation has been drafted. The BRD is a foundational delivery document — it must be reviewed and approved before functional design begins.

## Required Inputs

- Discovery session summary (complete)
- Module recommendation report
- Customer name, industry, project name/code
- In-scope business process areas
- Key stakeholders and their roles
- Any explicitly stated requirements from the customer
- Known constraints (timeline, budget, technical limitations)
- Known integration requirements (which external systems)

## Process

1. Compile requirements from discovery into categorized groups (functional, integration, reporting, data migration, technical).
2. Write each requirement as a clear, testable statement (not a vague wish).
3. Assign a priority to each requirement (MUST HAVE / SHOULD HAVE / NICE TO HAVE).
4. Define success criteria for the implementation at the business level.
5. Define the scope boundary clearly (in scope, out of scope).
6. List open items that need customer confirmation before the BRD can be finalized.

## Output Format

## Validation Rules

- Every requirement must have an ID, a clear statement, a priority, and a source reference
- Requirements must be specific and testable (not "better reporting" but "real-time inventory valuation report available to Finance Manager")
- Assumptions section is mandatory; if none, write "None identified — customer confirmation required"
- Open items must be present if any gap exists in the discovery data
- Version must be 0.x for all AI-generated drafts; 1.0 is only assigned after full review and approval

## Risk Checks

- Flag if fewer than 10 functional requirements are captured (likely incomplete)
- Flag if integration requirements section is empty but discovery mentioned external systems
- Flag if data migration is not addressed when the customer is replacing an existing ERP
- Flag if reporting requirements are vague ("standard reports only")

## Do Not Do

- Do not invent requirements not mentioned in discovery
- Do not mark any section as "Approved" or "Final"
- Do not include implementation design decisions in the BRD (the BRD captures WHAT, not HOW)
- Do not omit the Open Items section even if it feels empty

## Example Output

> FR-001: The system must allow the Accounts Payable team to record and approve vendor invoices electronically, with a minimum of two-level approval for invoices over $10,000. Priority: MUST HAVE. Source: Discovery Session 1 — AP pain points discussion.
